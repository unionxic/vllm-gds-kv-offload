### 09 KV 오프로드 정책 실험 보고

가중치를 매 forward 스트리밍하는 구성 위에서 KV를 SSD에 저장했다가 프리픽스 적중 시 읽어 오는 것이 이득인지, 손해라면 어디서 새는지, 무엇을 저장해야 하는지를 측정한 기록. 결론은 세 줄로 요약됨.

- KV를 SSD에 두고 적중 시 읽는 것은 처음 측정에서 재계산보다 느렸음. 원인은 디스크 대역폭도 읽는 양도 아니고, 로드가 끝난 순서대로 요청을 내보내는 스케줄러가 배치 파도를 쪼개 forward를 늘린 것.
- 같은 파도의 로드가 모두 끝날 때까지 계산을 미루는 게이트를 스케줄러에 넣자 forward 수가 기준선으로 돌아오고 KV 로드가 재계산보다 빨라짐. 전부 반복 워크로드에서 2.5%, 재사용과 1회성이 섞인 워크로드에서도 0.6% 이득. 손해에서 이득으로 전환.
- 무엇을 저장할지 고르는 admission은 원인을 고치지 못하고 읽기 노출 횟수만 줄임. 게이트로 로드가 이득이 된 뒤에는 첫 적중을 포기하는 만큼 손해가 되므로, 저장 정책의 가치는 스케줄러 상태에 종속.

### 구성

| 항목 | 값 |
|---|---|
| 모델 | OPT-66B fp16, 132 GB |
| GPU | Quadro RTX 5000 16 GB, 상주 2층 |
| host 티어 | 56층 106.3 GiB, cudaHostRegister 정확 등록 |
| SSD 티어 | 6층 11.4 GiB, cuFile |
| GPU KV | 5.5 GiB, 480토큰 요청 5개가 한 파도 |
| KV 저장 | expfs 스펙, OffloadingConnector, cuFile |
| 프롬프트 | 16개, 프리픽스 448 + tail 32, decode 8토큰 |
| 라운드 | 1라운드 cold(저장), 2라운드 적중(로드) |

forward 하나는 host에서 GPU로 106 GiB, SSD에서 11.4 GiB를 옮기는 고정 비용 약 13초. 처리 토큰 수와 거의 무관.

### 측정 방법

처음에는 generate 두 번의 벽시계 차이로 prefill과 decode를 나눴음. 그 방식은 두 번째 호출 안의 prefill이 decode 몫으로 새어 들어가 "decode가 느려졌다"는 잘못된 결론을 냈음. 그래서 엔진 step을 직접 돌리는 계측기(run_phase_66b.py)로 바꿈.

- 모든 KV 읽기와 쓰기에 시작·종료 시각과 outstanding 기록
- step마다 가중치 SSD 읽기 바이트, KV 바이트, 출력 요청 수 기록
- 요청별 제출·첫 토큰·완료 시각 기록
- decode step과 KV 읽기의 실제 중첩 시간을 IO 구간 교차로 계산
- 라운드 경계에서 잔여 store가 0인지 확인

### 비용 분해: 세 가설 모두 기각

| 가설 | 흔든 것 | 결과 |
|---|---|---|
| 읽는 바이트에 비례 | 프롬프트 16 → 8 | 손해 24.5 → 16.2초, 34%만 감소 |

바이트를 절반으로 줄여도 손해의 3분의 2가 남음. 양자화로 바이트를 줄이는 방향이 정답이 아니라는 뜻.

### 구간 분리로 찾은 원인

| 2라운드 | 저장 안 함 | cuFile |
|---|---|---|
| wall | 449.4 s | 507.9 s |
| decode step에 겹친 KV 읽기 | 해당 없음 | 0.0초, 0.0 GiB |
| forward 수 | 32 | 38 |
| 파도 패턴 (forward별 출력 요청 수) | 0, 5, 5, 5, 5, 5, 5, 5 | 0, 1, 1, 5, 5, 5, 5, 5, 5, 4 |
| forward 평균 | 13.5 s | 13.3 s |
| 폴링 step | 4개 | 1,176개, 합계 0.4 s |
| 라운드 경계 잔여 store | 0 | 0 |

- decode 감속은 없었음. 기존 숫자는 측정 산물이라 폐기.
- 쓰기만 있는 1라운드는 기준선과 같은 444.0초. 저장은 공짜.
- 폴링 공회전은 합계 0.4초로 무시할 수준.
- 손해는 전부 forward 개수. 5개짜리 파도에서 KV가 먼저 도착한 요청 하나가 두 forward를 혼자 돌고, 나머지 넷이 두 forward 뒤에 합류. 먼저 나간 요청은 먼저 끝나 마지막에 4개짜리 forward를 하나 더 남김. 파도당 8개가 10개로 늘고, 파도 3개면 forward 6개 약 80초. 쓰기가 없어져 prefill forward가 18.7초에서 13.6초로 짧아진 이득 20초를 빼면 관측된 58.5초와 일치.
- 읽기가 디스크를 점유한 시간은 다 합쳐 34.6초, 최대 동시 8개. 디스크는 포화가 아님.

### 왜 그렇게 되나

vLLM 스케줄러는 매 step 준비된 요청을 전부 모아 forward를 돌림. KV 로드가 비동기로 끝나면 커넥터가 요청별로 완료를 알리고 스케줄러는 그 요청을 바로 승격. 다른 요청의 로드를 기다리는 개념이 없음. 가중치가 GPU에 있는 보통 서빙에서는 forward가 수십 밀리초라 준비된 요청을 먼저 돌리는 것이 맞고 첫 토큰도 빨라짐. 상류 이슈 41784와 RFC 43702가 이 폴링과 즉시 승격이 의도된 설계임을 확인해 줌.

우리는 forward 비용이 토큰 수와 무관하게 13초로 고정. 요청 하나를 혼자 돌리면 나머지 넷이 13초를 놀고, 합류 뒤에도 어긋난 종료가 forward를 하나 더 만듦. 보통 환경에서 공짜였던 선택이 여기서는 파도당 27초짜리 낭비.

### 처방: 파도 게이트

vLLM 포크의 스케줄러에 승격 검사 하나를 추가. 환경변수 VLLM_KV_LOAD_WAVE_GATE로 켜며 기본은 꺼짐.

- 수준 1: 자기 로드가 끝난 요청을 같은 파도의 다른 로드가 모두 끝날 때까지 승격하지 않음
- 수준 2: 로드가 없는 신규 요청도 동료가 로드 중이면 잡아둠. 재사용과 1회성이 섞인 파도용
- 상한 VLLM_KV_LOAD_WAVE_WAIT_S(기본 30초). 한 요청이 막혀도 나머지가 멈추지 않음

상류 PR 55724가 비슷한 문제를 다루지만 토큰 예산 소진 시점을 고치는 것이라 지점이 다름. 우리는 KV 블록 용량에서 막히고 로드 완료 순서가 문제라 승격 시점을 직접 잡음.

| forward 수 | 32 | 38 | 32 |
| 파도 패턴 | 0, 5×7 | 0, 1, 1, 5×6, 4 | 0, 5×7 |

게이트를 켜면 KV 로드가 재계산보다 11.2초, 2.5% 빠름. 예측값 430초와 일치. 파도의 prefill forward가 2,400토큰 계산 대신 tail 32토큰씩만 붙이며 5초 짧아지는 이득이 파도마다 남고, 게이트 대기는 합쳐 4.6초.

### 무엇을 저장할지: 재사용 이력 기반 admission

문헌(Marconi, HotPrefix, Baleen, S3-FIFO)이 공통으로 두는 출발점인 한 번만 보이는 항목 배제를 적용. 두 번째 관측부터 저장하는 seen_twice. 워크로드는 재사용이 치우치게 만듦. 16개 중 4개만 라운드마다 반복, 12개는 매번 새 토큰열. 3라운드. 게이트 없음.

| 라운드 | 재계산 | 전부 저장 | seen_twice | forward |
|---|---|---|---|---|
| 1 | 449.8 s | 447.6 s | 445.6 s | 32 / 32 / 32 |
| 2 | 449.0 s | 482.5 s | 445.4 s | 32 / 35 / 32 |
| 3 | 449.1 s | 482.6 s | 481.8 s | 32 / 35 / 35 |
| 합계 | 1,347.9 s | 1,412.7 s | 1,372.8 s | |

- 전부 저장은 반복 4개의 KV 3.9 GiB만 읽는데도 라운드당 33.5초 손해. 4개가 첫 파도에 몰려 그 파도가 세 번 쪼개짐. 적중한 요청의 첫 토큰이 32초에서 55초로 오히려 늦어짐.
- seen_twice는 라운드 1에서 아무것도 저장하지 않아 라운드 2가 재계산과 같고, 실제로 읽는 라운드 3에서 같은 33초 손해. 손해가 절반이 된 것은 읽기를 피한 덕분이지 원인을 고친 것이 아님.
- 디스크 사용은 39.4 GiB 대 3.9 GiB로 10분의 1이지만 쓰기가 공짜라 벽시계에 나타나지 않음.
- staged 전송에서는 링 슬롯 6개와 CPU 경유 8개로도 저장 대상 청크의 절반이 슬롯 압박으로 버려짐. 정책이 저장하라고 한 것의 절반만 실행됨.
- 전송 구현을 staged로 바꿔 전부 저장해도 손해 33초, forward 35개로 동일. 손해는 전송 경로와 무관.

### 섞인 파도에서의 게이트

수준 1 게이트는 재사용 4개와 1회성 1개가 섞인 파도를 지키지 못함. 1회성 요청은 로드가 없어 게이트 대상이 아니고 혼자 먼저 나감. forward 35개, 패턴 0, 1, 1, 5로 게이트 없을 때와 같음. 수준 2는 로드가 필요 없는 신규 요청도 동료가 로드 중이면 계산을 미룸.

재계산, 게이트 0, 1, 2 네 조건을 4 MiB 조각으로 같은 상태에서 비교. 16개 중 4개 반복, 12개 1회성, 3라운드.

| 라운드 | 재계산 | 게이트 0 | 게이트 1 | 게이트 2 | forward |
|---|---|---|---|---|---|
| 1 | 440.9 s | 441.2 s | 441.7 s | 442.0 s | 32 / 32 / 32 / 32 |
| 2 | 440.5 s | 477.2 s | 477.4 s | 437.8 s | 32 / 35 / 35 / 32 |
| 3 | 440.6 s | 477.1 s | 477.3 s | 437.9 s | 32 / 35 / 35 / 32 |
| 합계 | 1,321.9 s | 1,395.4 s | 1,396.3 s | 1,317.7 s | |

| 첫 토큰 중앙값 (라운드 2) | 재계산 | 게이트 0 | 게이트 2 |
|---|---|---|---|
| 반복 요청 4개 | 32 s | 55 s | 29 s |
| 1회성 요청 12개 | 199 s | 227 s | 196 s |

수준 2가 forward를 32개로 되돌리고 파도 패턴이 0, 5×7로 기준선과 같아짐. 라운드당 재계산보다 2.7초 빠르고, 게이트 없는 전부 저장보다 39초 빠름. 적중한 요청의 첫 토큰이 55초에서 29초로 돌아와 재계산보다도 빠름. 게이트 대기 합계 1.1초.

수준 2를 맞추는 데 네 번 실패했고 각각이 스케줄러 내부 동작에 대한 사실 하나씩을 남김.

- 검사가 정식 큐만 훑으면 같은 step에서 시작된 로드를 못 봄. 비동기 admit된 요청은 그 step이 끝날 때까지 지역 임시 큐에 있음
- 커넥터의 적중 조회가 비동기라 첫 조회는 "아직 모름"을 돌려줌. 그 요청도 곧 로드할 동료로 세야 함
- 스케줄러가 큐를 훑으며 로드 중인 요청을 지역 큐로 옮기므로, 뒤에 검사받는 요청 시점에는 정식 큐가 비어 있음. 로드 중 여부는 큐 위치가 아니라 요청 ID 집합으로 추적해야 함
- 검사를 조회보다 앞에 두면 재사용 요청까지 조회 전에 잡혀 로드가 하나씩만 시작되고 파도가 1, 1, 2, 2, 3, 3, 5로 흘러 들어감. 로드는 병렬로 시작하게 두고 계산만 미뤄야 하므로 검사는 조회 뒤에 있어야 함

### admission 결론의 수정

게이트 없는 상태에서 seen_twice가 손해를 절반으로 줄인 것은 로드가 손해였기 때문. 게이트 2에서는 로드가 라운드당 2.7초 이득이므로, 라운드 1에서 저장을 안 해 라운드 2의 적중을 포기하는 seen_twice는 그만큼 손해가 됨. 저장 정책은 스케줄러가 로드를 이득으로 만든 뒤에 디스크 용량과 쓰기 부담을 기준으로 따로 정할 문제이고, 벽시계 기준으로는 전부 저장이 맞음.

### 문헌과의 관계

- Bidaw(FAST 2026): 느린 계층 I/O가 끝나지 않은 요청이 준비된 요청을 막는 문제를 dual queue로 분리. 문제 정의가 우리 관측과 같음. 가중치는 GPU 상주 가정.
- Strata(OSDI 2026): 캐시 로딩 지연을 모르는 스케줄러가 시스템을 loading-bound로 만든다는 문제 정의. balanced batch와 bubble filling. 우리 게이트 수준 2가 balanced batch의 가장 단순한 형태.
- Revisiting Pipeline Parallelism for LLM Serving(OSDI 2026): 파이프라인 병렬 주제라 다르지만, 배치를 어긋나게 만드는 요청을 보류하고 보류 중 KV를 할당하지 않는 delay scheduling이 같은 지렛대.
- vLLM 이슈 41784: 디스크에서 KV를 읽을 때 GPU가 불필요하게 유휴가 되는 같은 증상. 미해결. RFC 43702는 폴링 구조가 의도된 설계임을 명문화.
- AttentionStore(ATC 2024)의 층 단위 선반입은 우리 조건에 적용 불가. 논문 식에서 프리픽스 적중은 새 입력이 0이라 필요 버퍼가 KV 전체로 발산. Bidaw가 같은 결론을 실측, Tutti는 SSD에서 층 단위가 버블을 오히려 늘린다고 보고.
- 어텐션 기반 토큰 선별(H2O, SnapKV, PyramidKV)은 저장 필터로 쓸 수 없음. SCBench(ICLR 2025)와 KVzip(NeurIPS 2025)이 재사용 시 붕괴를 실증. 쿼리 무관 선별(KVzip 정적 헤드 모드, DuoAttention)과 양자화(KIVI, KVQuant)만 저장 시점에 안전.
- 가중치 스트리밍과 KV 로딩이 스케줄러를 통해 서로를 악화시키는 조합을 정면으로 다룬 탑티어 논문은 조사 범위에서 없음. 이 빈틈이 기여의 자리.
